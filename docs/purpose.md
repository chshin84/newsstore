# newsstore의 목적 — 수집은 여기까지, 분석은 다운스트림

> 이 문서는 **왜 이 데이터를 모으는가**를 잊지 않기 위한 맥락 참고서다.
> **중요 — 아래 "분석·작업"은 전부 다운스트림 몫이다. newsstore는 수집까지만 한다.
> 이 문서를 이 레포의 할 일(백로그)로 오인하지 마라. 최종 목적을 공유해 수집 설계의 방향을
> 잡으려는 것이지, 분석·전략을 이 레포에서 구현해 달라는 요청이 아니다.**

## 흐름: 웹 → 로컬 DB → 분석 → 다양한 작업

1. **웹(수집) — newsstore(이 레포)의 범위.** 온갖 금융 뉴스(RSS + 네이버 검색 뉴스 + FMP 뉴스)를 수집해 Firestore에
   보존한다(1년 버퍼). **여기까지가 이 레포의 전부다.** (FMP 시장 가격·펀더멘털·컨센서스는 이 repo가
   아니라 로컬 레포 `DB-news-data`가 직접 수집한다 — 아래 2.)
2. **로컬 DB(적재) — 별개 레포 `DB-news-data`.** Firestore(1년 버퍼)에서 뉴스를 매일 당기고, FMP 시장
   데이터(가격·펀더멘털·컨센서스)를 직접 수집해 DuckDB에 영구 적재한다. newsstore는 컨베이어 벨트, 집 DB가 아카이브다.
3. **분석 — 다운스트림.** 뉴스맵(임베딩 델타)으로 섹터·테마·종목의 관심 이동을 선행 발견하고, 수집된
   정량 데이터(컨센서스 리비전·서프라이즈·가격 델타)로 후행 확정·사이징한다. **이 레포 밖.**
4. **다양한 작업 — 다운스트림.** 투자 전략·백테스트·신호·리포트 등. **이 레포 밖.**

## 경계 (범위 계약)

- newsstore가 **하는 것**: 수집 · 중복 제거 · PIT 보존 · 정적 확인 UI · **임베딩 벡터 계산**(분석이 아니라
  수집 산출물 — 다운스트림 재사용).
- newsstore가 **안 하는 것**: 분석 · 태깅 · 클러스터 · 스토리 · 신호 · 리포트 · 전략 · 백테스트.
  전부 다운스트림이다.
- 데이터를 "분석 목적을 감안해" 모으되(무엇을 PIT로 남길지 등 수집 설계에 반영), **분석 자체는 절대 이
  레포에서 하지 않는다.**

## 왜 넓게, 왜 PIT로 모으나 (수집 설계의 근거)

- **넓게**: 뉴스맵이 어디로 관심이 이동하는지 놓치지 않으려면 광범위한 뉴스가 필요하다(FT·WSJ 등 접하는
  많은 뉴스 + 개별 종목 뉴스).
- **PIT로**: 컨센서스·목표가·등급 스냅샷은 FMP가 과거값을 주지 않아 backfill이 불가하므로 PIT 적재가
  필수지만, **그 수집은 `DB-news-data`의 몫이다.** 반면 from/to·filingDate로 소급 가능한 것은 다운스트림이
  필요할 때 당긴다. newsstore에서 PIT가 뜻하는 것은 수집 시점의 뉴스 원문을 가공·삭제 없이 보존하는 것뿐이다.
- 팩터의 PIT 수집 설계는 이 저장소를 떠나 `DB-news-data`가 소유한다(이 저장소에는 뉴스와 임베딩만 남는다).
